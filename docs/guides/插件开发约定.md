# 插件开发约定

> 面向插件作者。核心原则：**插件拥有什么，就必须负责清理什么**——底座只保证机制，不替插件擦屁股。

## 一、生命周期与清理钩子

| 钩子 | 时机 | 用途 |
|---|---|---|
| `register(ctx)` | 依赖就绪后、服务挂载前 | 初始化（读 ctx.config、订阅 onConfig） |
| `onStart(ctx)` | 全部插件注册完成后（boot 阶段二，按依赖拓扑序） | 启动资源（定时器、连接、子进程） |
| `onStop(ctx)` | 卸载时 | **清理**（与 onStart 相反序） |
| `ctx.effect(callback)` | register/onStart 内调用 | 注册副作用，**LIFO 自动撤销**（卸载时，onStop 前后都会执行） |

## 二、必须清理的资源清单（对照自查）

| 资源 | 清理方式 |
|---|---|
| **定时器**（setInterval/setTimeout） | 存句柄 → onStop 或 effect 里 clear；**否则卸载后仍 tick，是内存泄漏头号来源** |
| **事件订阅**（ctx.events.subscribe / services.subscribe / bus 订阅） | 保存返回的取消函数 → 卸载时调用；或 `ctx.effect(() => unsub())` |
| **文件句柄**（fs 打开/追加流） | onStop 里 close |
| **子进程**（console.exec 之外的 spawn/exec） | onStop 里 kill |
| **网络连接 / WebSocket** | onStop 里 close |
| **第三方资源**（数据库连接等） | onStop 里释放 |

## 三、推荐模式（三选一，按场景）

```ts
// 模式 A：effect（最省心，LIFO 自动撤销，卸载必执行）
async register(ctx) {
  const timer = setInterval(...);
  ctx.effect(() => () => clearInterval(timer));  // 须返回 dispose，勿写成 () => clearInterval(timer)
  const stop = ctx.events.subscribe(...);
  ctx.effect(() => stop);  // subscribe 返回的取消函数可直接作为 dispose
}

// 模式 B：onStop 显式清理（需要按序/异步清理时）
async onStop() {
  clearInterval(this.timer);
  await this.conn.close();
}

// 模式 C：混合——onStart 建资源 + onStop 对称销毁
async onStart(ctx) { this.watcher = fs.watch(...); }
async onStop() { this.watcher?.close(); }
```

## 四、硬约束

1. **卸载后不得再有活动**：卸载后定时器/订阅/句柄必须归零；底座会摘除服务订阅器和事件订阅，但**插件自己的资源靠插件自己清**
2. **effect 优于裸写**：能用 `ctx.effect` 就用——它保证 LIFO 撤销、且 onStop 无论成败都会执行（可逆副作用）
3. **onStop 幂等**：重复调用不得报错（底座可能在级联卸载时多次触发）
4. **禁止全局泄漏**：不在模块顶层建全局定时器/连接（热重载时旧模块的残留会失控）

## 五、反例与正例

```ts
// ❌ 反例：定时器裸奔
async register() { setInterval(job, 1000); }   // 卸载后还在跑

// ✅ 正例：effect 托管（返回 dispose）
async register(ctx) {
  const timer = setInterval(job, 1000);
  ctx.effect(() => () => clearInterval(timer));
}
```

## 六、底座已代管的（插件无需操心）

- 服务订阅器（service-call 响应）：注册时挂、注销/卸载时自动摘除
- 事件总线订阅（ctx.events.subscribe 返回的取消函数仍需插件自己保存——见上）
- 服务绑定：提供方卸载自动摘除
- onConfig 订阅：返回取消函数（插件自己决定何时取消）

## 七、分层（防写错插件）

当前实现（2026-08）：

| 层 | 插件 | 服务名 | 职责 |
|---|---|---|---|
| 身份 | `agent` | `agent` | scope + 绑 session |
| 记忆（会话） | `session` | `session` | 说过什么 + 会话元数据（title / workspace） |
| 记忆（经历） | `memory` | `memory` | 跨会话经历桶：breath / 衰减 / hold·trace（对照 Ombre-Brain） |
| 拼装 | `prompt-context` | `promptContext` | 这一步模型看见什么 |
| 人格 | `persona` | `persona` | soul.md 式身份基线（多份切换，≤3000 字）；不管理记忆；`persona_create` / `persona_update` / `persona_switch` |
| 思考原子 | `primitive` | `primitive` | 思考提示词仓库；树 + 双向链 + 内部路由预览；工具 primitive_*；不注入 prompt-context |
| 循环 | `query-loop`（现行）/ `agent-loop`（已禁用，保留） | `agentLoop` / `queryLoop` | query：assemble → model → tools，直到 end_turn；可挂 hook |
| 轨迹 | `trajectory` | `trajectory` | 怎么跑出来的 |
| 工作区 | `sandbox` | `sandbox` | 玩具沙箱：文件读写不出 `$WH_HOME/sandbox` |
| 本地编程 | `dev-tools` | `devTools` | 真实工作区：bash / 读改文件 / grep / glob，登记到 tools |
| 工具盒子 | `toolbox` | `toolbox` | 配置脚本：打开文件夹 / git push 等，登记 `box.*` 到 tools 与 workflow |
| 网页 | `web-tools` | `webTools` | 搜索与阅读：outline → 按节 read；markdown/text |
| 绘图 | `krea` | `krea` | Krea 文生图：`krea_generate` / `krea_job`；Key 走 `WH_KREA_API_KEY` |
| 工作流调度 | `workflow` | `workflow` | 按图调度 + `exec`/`listNodes`；节点 ctx 可带 agentLoop。不登记工具、不内置 kind=agent |
| 工作流节点 | `workflow-nodes` | `workflowNodes` | 登记 echo / upper，提供 demoGraph |
| Web 开发流水线 | `web-pipeline` | `webPipeline` | 登记 web.validate / web.deploy / nitron.package；无窗口；`pnpm web-dev` |
| 文件树 | `file-manager` | `fileManager` | 浏览 `WH_WORKSPACE_ROOT` 目录树；点文件开 code-browser |
| 代码浏览 | `code-browser` | `codeBrowser` | 只读浏览工作区源码；可切 code-editor |
| 代码编辑 | `code-editor` | `codeEditor` | 读写工作区文本文件；语法高亮 |
| 产品 | `app-chat` / `app-ui` / `app-workflow` | `appChat` / `appUi` / `appWorkflow` | 聊天窗 / 工作流 Demo（人设在 persona，不在 app-chat） |

**组装器：** `query-loop`（现行）与旧 `agent-loop` 都对 `promptContext` 为必选 inject。默认组合禁用 `agent-loop`，由 `query-loop` 提供 `agentLoop`。结构债 #1–#5 已落地，见 [`planning/todo.md`](../planning/todo.md) 第二阶段。

禁止：

- 新增 `system-prompt` 插件或名为 `systemPrompt` 的服务
- 在 agent 插件里写循环 / complete / 存 prompt
- 在文档里把「可选降级」写成产品设计（那是债）

## 八、文档纪律

插件 HTML、README、契约注释只写**当前代码**。待办登记见 [`planning/todo.md`](../planning/todo.md) 与 [`planning/product-maturity.html`](../planning/product-maturity.html)。改代码时同步对应 `docs/plugins/*.html`，不要留下会把后续修改带去 `system-prompt` 的句子。

## 九、插件弹窗 UI（滚动条）

观测台通过 `obs/gui/electron/main.cjs` 的 `PLUGIN_CHROME_CSS` 向**所有插件弹窗**注入标题栏与全局滚动条样式。插件 `ui.content` **不要**使用系统默认滚动条。

| 规则 | 说明 |
|---|---|
| 默认 | 由壳注入细滚动条（`scrollbar-width: thin` + `::-webkit-scrollbar`），与观测台主窗口一致 |
| 可滚动区域 | 需要滚动的容器用 `overflow: auto` 或 `overflow-y: auto`；长代码区可加 `scrollbar-gutter: stable` 避免换行时抖动 |
| 隐藏滚动条 | 聊天日志、轨迹列表等「仍要滚轮、但不显示滑轨」的区域，在**该容器**上写 `scrollbar-width: none` 与 `::-webkit-scrollbar{display:none}`，不要写进全局 |
| 禁止 | 在单个插件里再写一套默认灰色系统滚动条；不要在 `html/body` 上放开 `overflow`（壳已 `overflow: hidden`，内容区自己管 flex + min-height:0） |

代码浏览 / 编辑共用布局见 `plugins/code-browser/src/view-chrome.ts`（`CODE_VIEW_CHROME_CSS`），编辑器经 `@wizard-harness/plugin-code-browser/view-chrome` 引用。
