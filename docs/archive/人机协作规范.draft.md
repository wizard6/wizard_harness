# 人机协作规范（草案）

> 状态：**draft（原始文件）** —— 本文件由 AI 自由发挥，仅供给人类阅读。
> 人类据此写出 ≤300 字的确认文件后，本文件即完成使命；实现阶段禁止参考本文件。

## 0. 这份文件是什么

- 它是 wizard_harness（类 deepseek-harness 的 AI Agent 基座）的人机协作契约草案。
- 它定义"人如何与 AI 一起让项目生长"，并且它自己也要遵守这套流程。
- 核心态度：**项目生长可控，宁慢勿乱，牺牲效率换确定性。**

## 1. 为什么需要这套规范

- AI 自由发挥很快，但方向不可控、返工成本高、人类难以追责。
- 人类写详细需求很慢，但意图明确、边界清晰、结果可预期。
- 分工因此定为：**AI 负责探索与执行，人类负责意图与确认。**

## 2. 三条铁律

1. **一切皆插件**：能力、工具、文档、规则都以插件形式存在，核心壳保持最小。
2. **一切可追踪、可观测**：每个动作留痕，每次变更可回放，每个决策可审计。
3. **人机确认环**：任何生长都必须走"AI 起草 → 人类确认 → 严格实现"闭环。

## 3. 文档生命周期（核心流程）

不是所有文档都要走确认环。按"受众与用途"分三类：

| 类型 | 用途 | 谁读 | 确认环 |
|---|---|---|---|
| 意图类（契约） | 需求、规则、功能定义 | 草稿→人类；确认文件→AI | **强确认环** |
| 参考/知识类 | 背景资料、库文档、已实现说明 | **AI 可直接读** | 无确认环 |
| 记录/观测类 | 事件日志、违规记录、归档 | 人与 AI 都可读 | 自动记录 |

- **意图类**决定"要什么"，是项目生长的唯一入口，必须经确认环。
- **参考/知识类**是留给 AI 读的资料（第三方文档、技术参考、历史实现），AI 直接作为上下文，不走确认环。
- **记录/观测类**由流程自动产生，只读留痕，支撑"一切可观测"。

意图类文档严格经过以下三个阶段：

| 阶段 | 角色 | 位置 | 约束 |
|---|---|---|---|
| 1. 原始文件 | AI 自由发挥 | `docs/drafts/{名称}.draft.md` | 不限长度与形式，尽情探索 |
| 2. 人类确认文件 | 人类手写 | `docs/confirmed/{名称}.confirmed.md` | **正文 ≤300 字**，只写意图与边界 |
| 3. 实现 | AI | 按确认文件产出 | **禁止参考原始文件** |

### 3.1 阶段一：AI 起草（自由发挥）

- AI 把可能性、方案、顾虑都写进草稿，不设限。
- **意图类**草稿的唯一读者是**人类**，用于帮助人类想清楚"到底要什么"。
- 草稿不进入实现，因此写得再长、再发散都没有关系。
- （参考/知识类不属于此列：它们本就是给 AI 读的，见 3.0。）

### 3.2 阶段二：人类确认（≤300 字）

- 人类阅读草稿后，用**不超过 300 字**写确认文件。
- 确认文件只写三样东西：
  1. **要什么**（目标与范围）
  2. **不要什么**（边界与禁区）
  3. **一句话理由**（可选）
- 不写实现细节 —— 实现细节是 AI 的事，但不得超出确认的意图。
- 300 字上限是刻意的：逼迫人类提炼真意图，防止把"伪需求细节"塞给 AI。

### 3.3 阶段三：实现（严格按确认）

- AI 只读确认文件，**禁止打开或参考草稿**。
- 实现必须在确认文件意图与边界之内；可补充操作性细节，但不得越界。
- 实现完成、人类验收通过后，草稿移入 `docs/archive/` 归档（保留为阅读记录）。
- 归档后该文档进入"已实现"状态，只有新的确认文件才能改变它。

## 4. 内化协作纪律（源自 ai-coding-skill v1.31）

> 来源：<https://github.com/wizard6/ai-coding-skill>。此处只内化与本项目
> "确认环 / 插件化 / 可观测 / 可控生长" 同构的可用部分，并按本项目语境改写；
> 不照搬其代码级细则。括号内为源规范编号，仅作溯源；执行以本文件文字为准。

### 4.1 沟通与确认（服务确认环）

- **沟通语言层级 L1–L4（7.28）**：L1 想法 · L2 抽象 · L3 详设 · L4 实现。AI 先判定人类话语所在层，回复与动手不得越级。确认环即层级闸门：人类意图(L1/L2) → 确认文件/设计(L3) → 实现(L4)；L3→L4 必须经确认，或用户明示"实现 / 写代码"。
- **先确认后改（7.7）**：未确认不改文件。确认 list 写清：改什么 / 哪些文件 / 不改什么 / 可选顺带项。含糊先问，不猜。
- **目的闸门（7.12）**：先站在用户角度写清"做成后用户实际得到 / 能决定什么"，再判断建议是否合适；不合适则拒绝并给替代项，不盲从。
- **分层输出 + 快速理解（7.11 / 7.13）**：回复先结论、再编号清单、按需展开详情；重点加粗；用完整直述，禁比喻与注水。

### 4.2 生长约束（服务可控生长）

- **薄宏观 · 约束内生长（7.25）**：AI 适合在约束内快速生长，**禁止无边界漫生**。**确认文件（≤300 字）即本项目的"薄宏观"**：目的 + 边界 + 契约 + 验收。中等/大事动工前，确认 list 必带薄宏观块。
- **锁 = 确认文件 + 效果/功能锁（7.24）**：已实现状态由确认文件锁定；外观/行为关键点另建 `docs/EFFECTS.lock.md` 与 `docs/FEATURE.lock.md`，改前必读，触锁须确认。
- **SSOT**：确认文件是唯一契约；多来源冲突取"更严且更短"，并记录变更。
- **量级省耗（7.21）**：先定 小事 / 中等 / 大事 与探路预算；缺文件/位置先问或查索引，禁无目标全仓搜；超预算停搜。省耗聚焦本身就是"牺牲效率换确定性"的一部分。

### 4.3 追踪与复盘（服务可观测）

- **索引驱动（7.22）**：维护 `docs/INDEX.md`（AI 定位地图，属参考类）。发现巨石/入口/热点 → 先问再写。索引只作线索、可能过期，关键路径须核对。
- **及时提示提交（7.23）**：工作区有未提交改动、或中等/大事改前，提示先提交，防错改叠加难回滚。
- **事毕复盘 + 落点确认（7.20）**：交付后从结果反推最小路径与可删步骤；可固化为规则 → **须确认落点后**才写（项目 / 全局 / 不写），未确认不写。
- **TodoList 终局必总结（7.26）**：本轮用过任务清单，结束必写 已做 / 未做 / 下一步。
- **固定操作脚本化（7.19）**：重复步骤（起服/校验/打包）进 `scripts/` + `docs/AI-OPS.md`；AI 先读后跑，禁每次临场重推。

### 4.4 质量纪律（服务插件质量）

- **根因（6.8）**：错 / 多 / 少改 → 一句根因 + 规避，写入 `.ai-context` 或 TODO，避免重复踩坑。
- **禁占位债（6.9）**：正式路径不留成片 TODO / 假按钮；意图用 md 或演示页，确认后再落正式。
- **无预期不优化（7.9）**：说不清期望效果则不做；自我优化须先写清效果，否则停。
- **依赖向内（3.7）**：core 不依赖插件，插件依赖 core；跨界走事件 / DTO，不反向引用。呼应"核心壳最小"。
- **一文件一类事 / 默认 ≤300 行（1.4 / 1.5）**：**单个文件默认不超过 300 行**；超限须写一句理由并计划再拆。按职责拆（布局/交互/数据/逻辑），**效果与内聚优先于行数**；禁为凑行数砍功能、禁假拆空壳。此为本项目最重要的硬约束之一。

## 5. 边界与禁止

**AI 禁止：**

- 没有确认文件就实现**意图类**文档。
- 实现时参考**意图类**草稿（draft）。（参考/知识类不在此限，见 3.0。）
- 自行扩大确认文件的范围，或替人类做确认。
- 确认文件含糊时靠猜 —— 应停下提问。

**人类禁止：**

- 绕过流程，口头要求 AI"直接按草稿做"。
- 用超过 300 字的内容塞入确认文件。

**冲突处理：** 实现与确认文件冲突 → 以确认文件为准；确认文件含糊 → 停下提问，不猜测。

## 6. 违规处理

- 任何一方违反本规范都是一次**事故**，必须留痕：记录到 `docs/logs/violations.log`（时间、违反条款、影响、处理）。
- AI 违规（如参考草稿）：该实现作废，回滚，从确认文件重做。
- 人类违规：AI 应拒绝执行并说明原因。

## 7. 插件规范（概要，细则后续走本流程补全）

- 每个插件一个目录：`plugins/{名称}/`，含 `plugin.json`（元数据）与实现。
- 统一注册接口：`register(ctx)`，由壳负责调用。
- 每个插件必须声明：**输入、输出、副作用、依赖、观测点**。
- 壳（core）只做四件事：插件加载、事件总线、观测记录、配置管理。

## 8. 观测与追踪（概要，细则后续走本流程补全）

- 统一事件流，事件格式：`{ id, ts, actor, action, target, payload, trace_id }`。
- 人机确认环本身也被观测：草稿生成、确认文件写入、实现提交，都是事件。
- 审计回放、指标面板等能力，本身也是插件。

## 9. 自迭代

- 本规范同样按本流程进化：新草稿 → 人类确认 → 更新规则。
- 每次规则变更必须记录：**改了什么、为什么改、影响了什么**。
- 规范不稳定期允许高频迭代，稳定后减少变更频率。

## 10. 目录结构约定

```
wizard_harness/
├── README.md              # 项目入口：定位 + 当前状态 + 下一步
├── core/                  # 核心壳（最小）：事件总线 + 配置 + 注册器
├── plugins/               # 组件（就近自包含：logic + api + ui + 专属观测）
├── obs/                   # 观测台（与 core/ plugins/ 平级对齐）
│   ├── spec/              # 观测框架规格（ObsSpec 契约）
│   ├── core/              # ★ core 观测台：注册表（registrySpec + RegistryPanel）
│   ├── plugins/           # ★ 各插件专属观测台（占位）
│   ├── cli/               # 通用 CLI 观测器
│   ├── tui/               # 通用 TUI 观测器（ink）
│   ├── gui/               # 通用 GUI 观测器（HTML+Electron，含 views/ 调用定义）
│   └── api/               # 通用 API 观测器（HTTP/SSE）
├── scripts/               # 固定操作脚本（配合 docs/AI-OPS.md）
└── docs/
    ├── INDEX.md           # AI 定位索引（参考类）
    ├── AI-OPS.md          # 固定操作手册
    ├── EFFECTS.lock.md    # 效果锁（已验收外观/交互）
    ├── FEATURE.lock.md    # 功能锁（已验收行为/契约）
    ├── drafts/            # 意图类草稿（只给人类看）
    ├── confirmed/         # 意图类确认文件（≤300 字，唯一契约）
    ├── reference/         # 参考/知识类（AI 可直接读，无确认环）
    ├── logs/              # 记录/观测类（事件、违规日志）
    └── archive/           # 已实现文档的归档（冻结历史）
```

## 11. 下一步

2. AI 只依据确认文件，产出最终版规则与项目骨架。
3. 项目正式进入"确认环"驱动的生长节奏。
