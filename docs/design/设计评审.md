# 设计评审问题清单

- 评审日期：2026-08-19
- 范围：core（registrar / boot / harness / events / discovery / shell）+ obs/api + obs/gui
- 状态标记：⬜ 未处理 / ✅ 已处理

## 严重（语义/行为缺陷）

### S1 ✅ boot 的 PENDING 判定已结合运行时服务目录
- 位置：`core/src/registrar/boot.ts` `missingInjectInBatch`
- 已实现：新增 `extraServices` 参数（运行时已注册服务），bootPlugins 传入 `registrar.services.list()`；壳预注册的宿主级服务（如 bus）可被插件 inject，不再误判 pending；未注册服务仍判 pending（行为不变）
- 测试：`core/test/lifetime.spec.ts`（inject 宿主服务不误判 / 未注册仍 pending）

### S6 ✅ 服务生命周期分层（host / plugin）已实现
- 位置：`core/src/registrar/types.ts`、`registrar.ts`
- 已实现（Cordis 式）：`ServiceLifetime = 'host' | 'plugin'`；`ServiceRegisterOptions.lifetime`（默认 'plugin'）；`ServiceBinding.lifetime` 元数据（/services 可见）；壳注册长活服务显式传 `{ lifetime: 'host' }`（如 bus）；host 服务不随插件卸载消失
- 纪律文档化：`PluginContext.get` 注释写明「引用是借用，不保证存活——插件级服务应随用随取，宿主级服务可放心缓存」
- 测试：`core/test/lifetime.spec.ts` 4 项（元数据 / host 不随插件卸载 / boot 识别宿主服务 / 未注册仍 pending）；66/66 全过
- 说明：createHarness 默认不预注册宿主服务（harness.spec 锁定「初始无服务」），由壳显式注册

### S2 ✅ 两阶段生命周期已实现（boot：全部 register → 按拓扑序统一 start）
- 位置：`core/src/registrar/registrar.ts`、`boot.ts`、`types.ts`
- 已实现：`register(plugin, { deferStart: true })` 只注册不启动，返回 `RegisteredPlugin.start`（含失败回滚与 start 事件）；`bootPlugins` 先全部 register（服务全部挂载）再按拓扑序统一 start——提供方 onStart 可消费任意已声明服务（实证 S2 修复：A.onStart 取 b-svc 从 MISSING → found）
- 兼容：直接 `register()`（非 defer）行为不变（onStart 立即执行），已锁定测试未破坏；boot 中单个 onStart 失败回滚该插件、已启动的保持
- 测试：`core/test/lifecycle.spec.ts` 6 项；72/72 全过

### S3 ⬜ GUI 主进程 events 数组无界增长
- 位置：`obs/gui/electron/main.cjs` `const events = []`
- 问题：无上限追加，长跑（Agent 高频事件）内存泄漏；对比 registrar 内部 history 有 500 上限
- 建议：加环形缓冲上限（如 5000）

### S4 ⬜ 提供方看不到自己声明的 high 服务
- 位置：`core/src/registrar/registrar.ts` `visibleEntries`
- 问题：`if (e.access === 'high' && !trusted) return false` 未豁免提供方自身；untrusted 插件取不到自己的 high 服务（console 靠 trusted:true 才可用）
- 建议：high 门槛只约束他方，提供方对自己的服务始终可见

### S5 ✅ 可逆副作用（ctx.effect）已实现
- 位置：`core/src/registrar/registrar.ts` `makeContext` / `unregister` / `register`
- 已实现：`PluginContext.effect(callback)`（Cordis 语义）——callback 立即同步执行，返回值（若有）为撤销函数；effect 链存 registrar 层（`effects: Map<pluginId, dispose[]>`，根治 onStop fallback 丢失）；卸载时 LIFO 执行、finally 兜底（onStop 抛错也清理）、单个 dispose 异常隔离；onStart 失败回滚同样撤销；卸载后 effect 链清理、重注册不残留
- 测试：`core/test/effects.spec.ts` 7 项（自动撤销订阅 / LIFO / onStop 抛错兜底 / dispose 隔离 / ctx 透传 / 回滚撤销 / 重注册不残留）；62/62 全过
- 边界（未解决，另行处理）：effect 撤销的是"注册出去的副作用"，撤销不了"已发出的引用"；引用失效感知由 `service-unregister` 事件（已存在）的消费侧接入补齐

## 中等（设计不一致/性能）

### M1 ⬜ 事件落盘同步阻塞
- 位置：`core/src/events/persistence.ts` `createFileSink`（appendFileSync 挂在同步 bus.emit 上）
- 问题：高频事件会卡住整条总线
- 建议：异步/批处理落盘，或由壳决定落盘策略

### M2 ⬜ 双依赖声明系统
- 位置：`core/src/registrar/types.ts` `manifest.dependencies` vs `inject`
- 问题：id 级（只警告）与服务级（硬约束）语义重叠、强度不一，"半残能力"
- 建议：dependencies 升级为硬校验，或废弃、只留 inject

### M3 ⬜ /state 插件列表语义混杂
- 位置：`obs/api/src/main.ts` `/state`
- 问题：`plugins` 来自文件历史（currentPlugins），`runtime.loaded` 来自 harness，历史残留（plugin-a）与实时状态并存易误导
- 建议：统一为单一语义

### M4 ⬜ ctx 三种取服务路径冗余
- 位置：`core/src/registrar/registrar.ts` `makeContext`
- 问题：`ctx.get(name)` / `ctx.services.get(name)` / Proxy 属性 `ctx.logger` 三条路径
- 建议：明确主路径（Cordis 为 get+属性），或收敛

### M5 ⬜ tailEvents 每次轮询全量读文件
- 位置：`core/src/events/reader.ts` `tailEvents`
- 问题：每 500ms `readFileSync` 全量读盘再从 offset 切片
- 建议：按文件 size 增量或维护句柄偏移

## 轻（可接受但留意）

- 问题：服务在 `plugin.register()` 返回后才挂载（api 是对象内部引用，实际影响小）

- 位置：`core/src/events/dispatcher.ts`（console.error）、`core/src/shell.ts`（console.warn）
- 问题：core 应只发事件，输出由壳决定

### L4 ⬜ config 浅冻结
- 位置：`core/src/harness.ts` `Object.freeze({ ...config })`
- 问题：嵌套对象仍可改
