## P0 · 事件化 RPC 权限绕过（必修）

**现象**：`attachServiceHandler`（`registrar.ts:218-260`）的总线订阅器只检查 `e.action === 'service-call'`、`e.target === name`、`requestId`、`method`、`targetProvider === providerId`，**从不检查发起者**。`console` 是 `high` 权限服务（untrusted 插件经 `ctx.get('console')` 拿不到），但任何插件可伪造事件直达执行：

```ts
// untrusted 插件：ctx.emit 的 actor 自动为 plugin:<id>，不经过 callService 的可见性路由
ctx.emit({
  action: 'service-call', target: 'console',
  payload: { method: 'exec', args: [...], requestId: 'x', providerId: 'console' },
});
```

`attachServiceHandler` 会照单执行 `console.exec`——权限门被"借道事件"绕过。

**根因**：`callService`（发起侧）做了可见性路由（`visibleEntries` 过滤 high），但执行侧订阅器是"零直接引用"监听，没有镜像同一套校验；两条机制拼合时漏了执行侧。

**修复方案**：执行侧补一套与消费侧 `visibleEntries` 同构的校验，在 `attachServiceHandler` 分发前拒绝越权请求：

```ts
const viewerId = e.actor?.startsWith('plugin:') ? e.actor.slice('plugin:'.length) : 'shell';
const trusted = viewerId === 'shell' || registry.get(viewerId)?.manifest.trusted === true;
const entry = bindings.get(name)?.get(providerId);
if (!entry) return;
if (!isBindingVisible(entry, viewerId)) return;                                  // scope 门槛
if (entry.access === 'high' && viewerId !== providerId && !trusted) return;      // high 门槛（提供方自见豁免）
```

新增测试：untrusted 插件伪造 `service-call` 调 high 服务 → 被拒；trusted / 提供方自己 / shell 发起 → 放行。

## P1 · registrar 职责拆分（结构性）

**现象**：`registrar.ts` 一个闭包同时承担四块独立职责：

1. 插件生命周期：`register` / `unregister` / `reload` / `start` / `cascadeVictims`
2. 服务注册表：多提供方 `bindings` + 懒加载 `factory` + 权限/作用域可见性
3. 事件化 RPC 传输层：`callService`（调用方，~45 行）+ `attachServiceHandler` / `detachServiceHandler`（执行方，~50 行），协议含 `service-call` / `service-result` 事件名、`requestId` 关联、超时、`setImmediate` 隔离
4. 配置管理：`mergedConfig` / `updateConfig` / `configListeners` / `onConfig`

**修复方案**：把第 3 块抽成独立模块 `core/src/events/rpc.ts`，只暴露窄接口给 registrar：

```ts
// rpc.ts：事件化 RPC 传输层（不感知插件生命周期）
export interface RpcExecutor {                 // 执行侧：解析一条 service-call 到具体服务方法
  resolve(service: string, providerId: string): { instance: unknown } | undefined;
  authorize(service: string, providerId: string, actor: string): boolean; // P0 校验落这里
}
export function createRpc(rpc: {
  bus: EventBus;
  executor: RpcExecutor;
}): {
  call<T>(viewerId: string, trusted: boolean, service: string, method: string, args?: unknown, opts?: { timeoutMs?: number }): Promise<T>;
  attach(service: string, providerId: string): void;
  detach(service: string, providerId: string): void;
};
```

registrar 只负责：生命周期、服务注册表、配置。`ctx.call` / 壳侧 `call` 变成一行委托。`service-call` / `service-result` 事件名、`requestId` 协议常量内聚在 rpc.ts。收益：registrar 从 664 行降到约 450 行，RPC 可独立单测，权限校验与协议同处一地。

## P2 · 订阅器收敛（与 P1 同批做）

**现象**：`services.register` 无条件 `attachServiceHandler`（`registrar.ts:139`），每注册一个服务就 `bus.subscribe` 一次；即使项目从不使用 `ctx.call`，每个服务也白挂一个监听器。可选能力变成默认全局成本。

**修复方案**：把"每服务一个订阅器"收敛为"**一个全局订阅器 + 一张路由表**"：

- `createRpc` 内部只 `bus.subscribe` 一次，监听 `service-call`；
- `attach(service, providerId)` 只往路由表 `Map<name, Set<providerId>>` 登记一行，不产生新订阅；
- `detach` 删表项；路由表空时全局订阅器依旧存在（成本恒定 O(1)）。

这样"服务是否可被事件化调用"由挂载决定，成本不再随服务数线性增长，且 detach 语义天然支持热重载（旧提供方摘除后事件化调用自动落到新实现）。

## P3 · 删除死代码 CTX_OWN

**现象**：`registrar.ts:42` `const CTX_OWN = new Set([...])`，Proxy get（`registrar.ts:444-452`）里条件为：

```ts
if (typeof prop === 'string' && !CTX_OWN.has(prop) && !(prop in target)) { ... }
```

`CTX_OWN` 列出的成员（`config/effect/emit/get/services/events`）全部存在于 `base` 对象上，`!(prop in target)` 必然已拦截——`!CTX_OWN.has(prop)` 是永远不产生独立效果的死条件（也容易误导：新增 ctx 成员时还要记得同步它）。

**修复方案**：删除 `CTX_OWN` 与对应条件，Proxy 简化为：

```ts
get(target, prop, receiver) {
  if (typeof prop === 'string' && !(prop in target)) {
    const svc = pickVisible(prop, viewerId, trusted);
    if (svc !== undefined) return svc;
  }
  return Reflect.get(target, prop, receiver);
}
```

行为不变（有测试锁定），删掉的正是"没有原因的代码"。

## P4 · 收敛取服务路径

**现象**（设计评审 M4 的延续）：取/调服务有四条路径——`ctx.get(name)`、`ctx.services.get(name)`、Proxy 属性 `ctx.logger`、`ctx.call(service, method, ...)`。

**修复方案**：收敛为"**一条取 + 一条调**"：

- 取服务：只留 `ctx.get(name, providerId?)`；`ctx.services.get` 删除，`ctx.services` 退化为纯目录浏览（`getAll / providers / list / waitFor`，不含 get）。
- 属性语法糖（`ctx.logger`）保留：它是 cordis 语义（`ctx[prop] ≡ ctx.get(prop)`），文档已写明仅名字空闲服务生效。
- 调用：`ctx.call` 保留，语义与取服务不同（事件化 RPC），不算冗余。
- 契约同步：`PluginContext.services` 去掉 `get`；测试同步。

## P5 · 消除 reload 与 unregister 的级联重复

**现象**：`unregister`（`registrar.ts:540-571`）内部已实现级联（`cascadeVictims` + 递归 `unregister`）；`reload`（`registrar.ts:591-634`）为了拿到可观测的 `victims` 列表，先 `unregister(id, { cascading: false })` 关掉级联，再手动 `cascadeVictims` + 递归一遍——同一逻辑两份实现，后续改级联规则必须改两处。

**修复方案**：`unregister` 返回级联结果，reload 复用：

```ts
async function unregister(id, opts = {}): Promise<{ victims: string[] }> {
  // ...清理与卸载...
  const victims = cascadeVictims(id, provided);
  if (opts.cascading !== false) {
    for (const vid of victims) if (registry.has(vid)) { emit('inject-cascade', ...); await unregister(vid); }
  }
  return { victims };
}
```

`reload` 改为 `const { victims } = await unregister(id, { cascading: false })` 后，对 `victims` 逐个 `emit('inject-cascade')` + `unregister`（保持观测事件与返回结构不变）。

## key-based 架构对齐（2026-08-20 补充）

**依据**：cordis-primer 权威定义——"服务占据稳定的 `ctx.<key>`，其他插件**通过 key 查找服务而非导入具体实现**"；依赖注入、事件通信、插件定位均以字符串 key 为唯一连接媒介，插件之间零对象引用。

**符合度评估**：

| 维度 | key-based 标准 | 现状 | 判定 |
| --- | --- | --- | --- |
| 服务定位 | `ctx.<key>` 按服务名 key 查找 | `ctx.get('logger')` / `ctx.logger`（Proxy） | ✅ |
| 服务依赖 | 服务名 key 声明依赖 | `inject: ['logger']` | ✅ |
| 插件定位 | 插件 id 是 key | `Map<id, plugin>`、reload/updateConfig 按 id | ✅ |
| 配置注入 | 按 key 分片 | `config[pluginId]` 合并 | ✅ |
| 服务调用 | key 路由 | `ctx.call(service, method)` 事件化 RPC | ✅ |
| **事件订阅** | **按事件名 key 注册，只收匹配事件** | **`bus` 全量广播，插件须自己 `filter(e.action === ...)`** | ❌（已修） |
| 依赖表达 | 只有服务依赖 | 另有 `manifest.dependencies`（插件 id 依赖，仅警告） | ⚠️ 待定 |
| key 空间 | 服务名与插件 id 相互独立 | 缺省 `provides` 用插件 id 当服务名；`highAccessServices` 可写插件 id | ⚠️ 待定 |

**本次修正（已落地）**：补上事件订阅的 key 路由——`PluginContext.on(action, handler)` 按事件名（action key）精确订阅，只收到匹配事件；与 `ctx.events.subscribe`（全量观测流）并存，通信用 `on`、观测用 `subscribe`。实现为注册器内一张 `action → Set<handler>` 路由表（单总线订阅分发，不随订阅数增长）；监听器在插件卸载/回滚时随 effect 可逆链自动取消，手动取消幂等；单个监听器抛错隔离。新增 `core/test/events-key.spec.ts` 6 项测试（过滤/多订阅者/取消/卸载零残留/与全量流并存/异常隔离），94/94 通过。

**剩余偏离（待定夺，不改行为）**：
1. `manifest.dependencies`（插件 id 依赖，仅警告）与 `inject`（服务名依赖，硬约束）双体系——建议废弃或升级 dependencies 为硬校验（设计评审 M2）。
2. 缺省 `provides` 服务名 = 插件 id、`highAccessServices` 可写插件 id——两个 key 空间的便捷规则，建议文档化"服务名与插件 id 是两个独立 key 空间"。
3. 同名服务多提供方并存、`get()` 取插入序第一个——key 解析确定性弱（见上文 P 类诊断）。
