# 插件开发约定

> 面向插件作者。核心原则：**插件拥有什么，就必须负责清理什么**——底座只保证机制，不替插件擦屁股。

## 一、生命周期与清理钩子

| 钩子 | 时机 | 用途 |
|---|---|---|
| `register(ctx)` | 依赖就绪后、服务挂载前 | 初始化（读 ctx.config、订阅 onConfig） |
| `onStart(ctx)` | 全部插件注册完成后（boot 阶段二，按依赖拓扑序） | 启动资源（定时器、连接、子进程） |
| `onStop(ctx)` | 卸载时 | **清理**（与 onStart 相反序） |
| `ctx.effect(callback)` | register/onStart 内调用 | 注册副作用，**LIFO 自动撤销**（卸载时，onStop 前后都会执行） |

## 二、必须清理的资源清单（对照自查）

| 资源 | 清理方式 |
|---|---|
| **定时器**（setInterval/setTimeout） | 存句柄 → onStop 或 effect 里 clear；**否则卸载后仍 tick，是内存泄漏头号来源** |
| **事件订阅**（ctx.events.subscribe / services.subscribe / bus 订阅） | 保存返回的取消函数 → 卸载时调用；或 `ctx.effect(() => unsub())` |
| **文件句柄**（fs 打开/追加流） | onStop 里 close |
| **子进程**（console.exec 之外的 spawn/exec） | onStop 里 kill |
| **网络连接 / WebSocket** | onStop 里 close |
| **第三方资源**（数据库连接等） | onStop 里释放 |

## 三、推荐模式（三选一，按场景）

```ts
// 模式 A：effect（最省心，LIFO 自动撤销，卸载必执行）
async register(ctx) {
  const timer = setInterval(...);
  ctx.effect(() => clearInterval(timer));
  const stop = ctx.events.subscribe(...);
  ctx.effect(stop);
}

// 模式 B：onStop 显式清理（需要按序/异步清理时）
async onStop() {
  clearInterval(this.timer);
  await this.conn.close();
}

// 模式 C：混合——onStart 建资源 + onStop 对称销毁
async onStart(ctx) { this.watcher = fs.watch(...); }
async onStop() { this.watcher?.close(); }
```

## 四、硬约束

1. **卸载后不得再有活动**：卸载后定时器/订阅/句柄必须归零；底座会摘除服务订阅器和事件订阅，但**插件自己的资源靠插件自己清**
2. **effect 优于裸写**：能用 `ctx.effect` 就用——它保证 LIFO 撤销、且 onStop 无论成败都会执行（可逆副作用）
3. **onStop 幂等**：重复调用不得报错（底座可能在级联卸载时多次触发）
4. **禁止全局泄漏**：不在模块顶层建全局定时器/连接（热重载时旧模块的残留会失控）

## 五、反例与正例

```ts
// ❌ 反例：定时器裸奔
async register() { setInterval(job, 1000); }   // 卸载后还在跑

// ✅ 正例：effect 托管
async register(ctx) {
  ctx.effect(() => clearInterval(setInterval(job, 1000)));
}
```

## 六、底座已代管的（插件无需操心）

- 服务订阅器（service-call 响应）：注册时挂、注销/卸载时自动摘除
- 事件总线订阅（ctx.events.subscribe 返回的取消函数仍需插件自己保存——见上）
- 服务绑定：提供方卸载自动摘除
- onConfig 订阅：返回取消函数（插件自己决定何时取消）
