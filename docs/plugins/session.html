1. 用途与边界

一句话：会话的唯一追加日志。llm 要从这里投影历史；tools 的结果要写回来；agent 只绑定这条日志；agent-loop 只编排，不另存一份聊天记录。

管什么

  • 开会话 start
  • 追加 turn / message / tool-result
  • 只读 replay / deriveMessages
  • 广播 session/start、session/append

不管什么

  • scope / isolate（可见性在 core/src/scope）
  • 模型调用、工具执行、agent 循环
  • 磁盘持久化、compaction、fork/resume
  • 通用 UI 桥（弹窗只是说明页）

→
session发生过什么（本插件）
→
llm / tools / agent / agent-loop读写本日志

2. 提供的服务

服务名常量 SESSION_SERVICE = 'session'。消费方：ctx.session 或 ctx.get('session')。

方法作用失败
start({ id?, title? })新建会话，成为 currentid 重复抛错
append(kind, data?)追加一条冻结条目，seq+1未知 kind / data 非 JSON 对象
replay()只读返回该会话全部条目（保序）—
get(id) / list() / current()查找 / 列举 / 最近 start 的会话无则 undefined
deriveMessages(id)投影 kind===message 的条目（给 llm）未知 id 返回 []

条目形状

{ seq: number, time: number, kind: 'turn' | 'message' | 'tool-result', data: object }

约定（给后续插件，本层不强制 schema）：

  • turn → { phase: 'start' | 'end' }
  • message → { role: 'user' | 'assistant' | 'system' | 'tool', content: string }
  • tool-result → { callId, name, content, ok?: boolean }

6. 给后续 AI 的硬约束

  • 不要在 llm/tools/agent 里再造一份 messages[] 当真相源；只 append / replay 本服务。
  • 不要把 scope 标签写进 session 条目来「模拟隔离」；可见性走 createScope。
  • 不要在本插件加模型、工具、HTTP、SQLite，除非单独确认；薄切片故意不做。
  • 扩展事件类型（如 tool/call）应先改 contracts/src/session.ts 的 SessionKind，再改 store 白名单。
  • DSH 用 ctx.sessions（复数）+ 细事件名（user/message）；本仓库服务名是 session，kind 只有三类。对齐 DSH 是后续工作，不要 silently 改名。

7. 已知问题与非目标

已知问题

  • 不持久化：进程退出后 replay 为空。事件 jsonl 里可能有 session/append，但没有从 jsonl 重建日志的代码。
  • 无 flush / 崩溃恢复：与 DSH ctx.sessions.flush 不对齐。
  • 模块级 ctx：emit 闭包读插件模块变量；单进程单实例没问题，测并行或多实例会串。
  • get() 每次新句柄：同一 id 多次 get 得到不同 Session 对象，内部指向同一 entries 数组（行为正确，引用相等性不要当身份）。
  • 无按 scope 分桶：所有会话在一张全局 Map；多 agent 同时跑会看到彼此的 list()（应用层用不同 session id 区分）。
  • deriveMessages 很薄：不过滤 role、不拼 tool 轨迹，llm 接入时几乎肯定要加投影规则。

明确非目标（本切片）

  • YAML/DSH 全量 SessionEvent 目录、surface replace、compaction
  • 磁盘 JSONL/SQLite 后端
  • 通用弹窗 RPC（当前 ui 是静态说明页）
